# Jev 开源项目分析与实战取舍

分析日期：2026-09-27。范围为用户提供的五个 ZIP 快照；不逐个审计 awesome 列表中链接的外部仓库。源码展开到 `projects/`，原 ZIP 保留不变。ZIP 的 SHA-256、大小见 `../experiment/jev_practice/results/manifest.json`；压缩包没有 Git 提交历史，因此不把 main 文件名当作版本号。

本轮目标是为第 30 期 slide 增加可重跑的实战。用户选择先完成离线部分。这不是法律文档论文复现，也未确定正式研究协议。下面的难度是按当前 Windows / Python 3.12 / Node 22 环境判断。

## 总体选择

| 项目 | 实际定位 | 最短运行路径 | 完整系统门槛 | 本轮落地 |
|---|---|---|---|---|
| awesome-jev | 案例目录，另有 Jev 标签建议脚本 | 本地目录构建与离线测试 | 在线标签分析需 GitHub / Jev 网络调用 | 分析及原仓库测试 |
| fast-jev-compaction 0.2.0 | 托管 Jev 驱动的工具历史裁剪 | npm 构建 + 注入 JevAsker | 真实判断需 API；Claude hook 另需宿主支持 | 实际库调用、输入输出对照、错误路径 |
| jev-chat-jarvis v1.4（README 标注） | Android 采集 + 判断 + 生成 + 候选排序 | Python 问题构造，无依赖模型 | Android SDK / 真机权限 / 判断及生成接口 | 原题目构造代码运行，导出请求 |
| JEVfire 0.1.0 | 冻结语言模型的候选 token 打分 | Python 验证 / 解码纯逻辑 | 服务端 CUDA + vLLM；浏览器版 WebGPU + 模型下载 | 原解码器运行，阈值拒答演示 |
| NanoJev 0.0.1（包版本） | 训练式开放决策模型及游戏环境 | HTTP 静态服务播放现有轨迹 | checkpoint + PyTorch / Transformers；参考训练环境为 A100 | 迷宫 / 贪吃蛇三模型本地回放 |

优先选 compaction，因为流程完整、依赖少、讲解价值高。NanoJev 的现成回放适合展示动作概率与环境反馈。JEVfire 补充“有限选项保证结构，不保证正确”的例子；Jarvis 补充“判断与生成分工”。

## 1. awesome-jev：找选题，也有可复用的证据门控

入口：`projects/awesome-jev-main/README.md`、`categories/`、`tags.json`、`scripts/build-readme.py`、`scripts/jev-ray.py`。

README 是分类文件汇总产物；真正维护入口在 categories。`build-readme.py` 生成总表并同步 CONTRIBUTING 的标签词表，直接执行会改上游文档，因此本轮只运行其测试，不重写快照。`jev-ray.py` 不是普通静态目录脚本：它取仓库摘要，问 agent/type 两道 choice 与 agent_evidence/multi_agent 两道 noul，再通过门槛决定是否建议标签，保留人工标签优先。

可迁移价值：把“看到关键词就分类”改成“候选标签 + 明确证据题 + 代码门控”。很适合后续做论文目录或开源项目分类；需先定义标签、允许拒答和人工复核。它不证明被收录项目可运行，README 也明确声明收录不等于质量审核。

许可：README 声明 MIT，但此 ZIP 没有独立 LICENSE 文件，单独记录这一缺口。目录中的外链内容仍适用各自许可。本轮不自动克隆其数百个链接，也不把目录里的效果宣传当成实验结果。

验证：原仓库 26 项离线测试通过。首次运行有 4 项因本地 HTTP 假服务器被代理返回 503 而失败；对 localhost / 127.0.0.1 设置 NO_PROXY 后重跑通过，未修改上游实现或测试。

## 2. fast-jev-compaction：最适合首个实战

源码证据：`src/state.ts` 收集工具调用并配对结果；`src/compact.ts` 的 `questionsFor` / `decideCall` / `applyDecisions` 实现两道 noul 和三种动作；`src/request.ts` 构造请求；`hooks/fast-jev.ts` 处理宿主回退。MIT，TypeScript，无运行时 npm 依赖。

工作链路：聊天历史 → 首条及最近消息固定保留 → 每个旧工具调用问“调用是否保留”和“完整结果是否保留” → 阈值分支 → 重建历史。结果分数过线则整对保留；仅调用过线则截短结果；都不过线则成对删除。文本消息在输出中保留原文。发送给模型的 state 会省略工具结果正文，必要时缩减输入，所以模型并非看到完整原始历史。分批时还会重复发送同一 state。

实战：合成 4 对工具调用，覆盖删除、截短、保留、最近固定保留。使用上游导出的 `compact`，注入人工固定概率，实际输出从 8,144 字符降至 316 字符（上游计数口径，96.12%）。这只是特意构造的样例，不能推出 token / 费用节省，更不能推出裁剪后的任务成功率。

验证：原库 29 项测试通过；本项目断言约束文本、唯一错误证据、调用结果配对均保留，缺失回答抛错。没有安装 Claude hook，也没有接管用户聊天历史。

边界：`noulAnswer` 检查数值有限但未检查 [0,1]，若后续接不可信兼容后端，应额外验证范围。结果正文被省略会使“结果仍重要吗”判断缺乏证据；应在真实任务里测误删和最终任务成功率，而不是只看缩短比例。错误由库抛出，宿主 hook 才负责回退，不应误以为库自动兜底。

## 3. jev-chat-jarvis：判断模型不负责写回复

源码证据：`app/src/main/java/com/jev/probe/jev/JevClient.kt` 依次调用 ReplyClient 草拟与 JudgeClient 排序；`JudgeClient.kt` 解析概率并排序；`tools/jev/questions.py` 提供 7 道判断题、最近 10 条消息构造及 3 候选的排序题。MIT，Kotlin / Android，Python 脚手架可单独运行。

链路：无障碍 / 本地 OCR 采集 → state（聊天及可选背景）→ 判断模型回答意图、紧张程度等 → 生成模型写 3 条候选 → 判断模型选候选 → 用户决定是否发送。因此它不是“Jev 会聊天”，Jev 只承担判断部分。

本轮直接运行 Python 原函数，输入合成同事对话，导出 7 题及 1 道候选排序请求。候选由人工写好，没有生成回复、没有模型打分，也没有发送消息。校验最近 10 条截断和候选数必须为 3。

边界：README 的 v1.4 描述已经排除微信；仓库 CLAUDE.md 仍包含旧版微信适配说明，存在文档时间冲突，不能把旧说明写成当前支持事实。Python 简化状态与 Android 的背景 / 历史增强不是完全相同的端到端实现。主观“真实意图”标签及关系风险分并不是真实心理状态；后续应评估标注一致性和错误建议率。本轮不搭 Android 环境。

## 4. JEVfire：不训练，也能做有限选项推断

源码证据：`jevfire/models.py` 的 DecisionField / DecisionRequest 限制平坦 boolean/enum schema；`core.py` 的 `make_labels` 验证 token 单一且可回解，`build_prompts` 为字段构造共享前缀，`normalize_scores` / `decode_choice` 归一化并映射回业务值。MIT，服务端 Python + vLLM；Web 目录另有 WebLLM / Three.js 实现。

它使用已有模型的语言模型头，不等同于 TypeSafe Jev 的模型架构或 RLCD 训练复现。字段独立打分，程序装配 JSON；跨字段依赖需要业务代码另行协调。服务端是否复用前缀取决于引擎缓存，不能把多个字段等同于保证只做一次前向。

实战：直接调用上游 `decode_choice`，用人工 logprob 样本演示 billing/technical/unknown。最高概率 0.82 且阈值 0.70 时选 billing；最高概率 0.36 时返回 `value: null`，同时保留 `selected_value` 用于诊断。缺失候选分数则抛 BackendError，不偷偷填默认值。这里的候选 token id 也是人工夹具，不代表任何真实 tokenizer。

验证：`tests/test_parallel_decoding.py` 22 项通过（补装 pytest-asyncio 后包含异步模拟后端测试）。这覆盖逻辑与模拟传输，没有启动 CUDA 或下载模型。归一化概率不是正确率校准；上游 71 ms / 10.3× 等数字没有在本机复现，不写成本轮成绩。

## 5. NanoJev：训练项目与回放要分开讲

源码证据：`scripts/train_toy_decisions.py` 的 DecisionModel 将候选路径打包，经 backbone 取末端表示，用 scalar head 打分，choice 可用 set attention；布尔分支构造 [0,z] logits；训练采用目标分布交叉熵。该参考实现重复前缀，源码注释也把 tree sharing 标为另一项优化。`serve_decisions.py` 提供本地 checkpoint 服务；`web/dev/side-by-side.js` 读取 JSON、校验帧并绘制回放。

MIT 代码；模型与数据发布位于 README 指向的 Hugging Face 仓库，其下载及使用条款需要另外核对。README 的统一游戏 checkpoint 是 `unified-games-v1` / step-400；包里的 0.0.1 不是 checkpoint 版本。完整推理还需权重，ZIP 的回放 JSON 本身不是模型。

本轮搭本地静态回放入口，核验迷宫 / 贪吃蛇轨迹结构和 SHA-256。50×50 迷宫快照中记录 NanoJev 225、Jev 2,738、未微调基座 4,726 次尝试；这是一个被选中展示的轨迹，且有共享探索代码，不是完整测试集平均值，也不是本轮重新调用模型获得。不能从这一个画面得出 NanoJev 普遍优于 Jev。

后续完整推理路线：核对 GPU 和包版本 → 下载固定 revision 的 checkpoint 与 tokenizer → 启动推理服务 → 使用相同种子与控制器重跑 → 再比较任务成功率、碰撞和端到端耗时。当前没有安装 PyTorch，不以安装大量训练依赖作为离线演示前提。

运行入口：`../experiment/jev_practice/README.md`。结果 JSON、运行清单和截图可追溯。slide 新增段放在原 38 页之后，原未来段顺延。上游 PaperDance 数值仍是素材作者原有实测声称，本轮没有复测。
