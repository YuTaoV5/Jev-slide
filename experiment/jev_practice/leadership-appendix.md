## 领导追问备忘（跨页）

以下为预判问题与建议回答，未发生的讨论不得记作已确认决策。

| 问题 | 建议回答 | 还需要收集的证据 |
|---|---|---|
| 既然无模型 162 次更好，为什么还讲 Jev？ | 这是重要的对照结果。游戏展示暴露了归因问题；kernel 的语义判断需用自己的案例验证，不预设模型优于规则。 | 同一 kernel 案例的规则、现有 Agent、加 Jev 对照 |
| NanoJev 是不是 Jev 的开源权重？ | 不是。它是基于 Qwen3-0.6B 的独立实现；不能代替 TypeSafe 模型做性能或能力背书。 | 两者固定版本、数据与适用边界 |
| 是否需要自己训练？ | 第一阶段先验证任务定义。可用规则与现有流程建基线；Jev 接口、可本地部署的小模型是可比较的选项。 | 标签数量、部署约束和基线错误分布 |
| Jev 能否完全离线？ | 当前材料没有验证 TypeSafe Jev 本地部署路径。本次离线的是上游概率回放与控制器，不是 Jev 推理。若必须离线，应评估可部署模型，不能拿 NanoJev 的部署能力替 Jev 承诺。 | 厂商交付条件、数据外发政策、本地模型实测 |
| 日志能不能送外部服务？ | 由组织数据治理确认允许的字段；本方案优先本地抽取、最小化片段。未经确认就继续纯离线评估，不承诺原始日志外发。 | 字段分级、脱敏规则与授权范围 |
| 对中文、汇编、寄存器值是否可靠？ | 当前没有本项目测量。精确计算与符号化交给工具，语义判断按语言、故障族与平台单独评估。 | 分层标注集、失败样本与工具校验 |
| 如何避免“看起来很自信”的错误？ | 检查证据充分性和反证，设置候选不足出口；在校准集选择门槛，在留出集报告误导率及覆盖率。单个概率不保证正确。 | 置信分桶、risk–coverage、严重类错误复查 |
| 有多少加速、多少钱、几周完成？ | 没有真实 kernel 案例与部署约束之前不给收益和排期承诺。先盘点数据、接口与基线耗时，再出资源估算。 | 人工确认时间、工具墙钟耗时、API 成本、失败开销 |
| 是否替代 kernel 专家？ | 专家仍定义问题、核实证据和验证根因。目标是减少无效查找，让专家更早看到高价值证据。 | 人工采纳率、误导返工时间、复核一致性 |
| 最高候选不正确怎么办？ | 保留多假设、OTHER 与扩检出口；原始证据不因低分删除。候选召回与排序分别验收。 | Recall@K、Top-k、错误分流及候选缺失样本 |
| Jev 升级后能直接替换吗？ | 不直接沿用旧结论。固定版本、题目、阈值、输入 schema 和控制器，升级后跑回归与切片评估。 | 版本化决策日志、回归集、回滚记录 |
| 试点失败有什么沉淀？ | 可复核的证据索引、真实 worker、历史案例标签和评估链仍然有价值，决策适配器可撤回或替换。 | 可重放案例包与基线报告 |

## 讲述口径自检

- 可以说：NanoJev 在所选轨迹 225 次到达，Jev 为 2,738 次；本地常数概率对照为 162 次。
- 不说：NanoJev 推理快 12 倍、判断必然更准、Jev 已在 kernel 定位提升效率。
- 可以说：原始两条轨迹的动作与反馈已由相同控制器重放验证；常数对照实际离线执行。
- 不说：本机重新运行了两个模型或做了完整公平基准测试。
- 可以说：当前 AI4-Loc 具备任务和报告界面，核心分析路径仍是 mock；新方案拟先接入 worker。
- 不说：界面的固定评分已经证明了定位精度，或 kernel 目录当前具备完整可分析源码。
